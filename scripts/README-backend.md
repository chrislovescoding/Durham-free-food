# Public data ingestion

Install Python 3.11+ dependencies with `python -m pip install -r requirements.txt`, then run `python scripts/refresh.py`. Run checks with `python -m unittest discover -s tests -p 'test_*.py' -v`.

The crawler reads Durham Students' Union's public [society directory](https://www.durhamsu.com/groups/studentgroups/), visits profiles with at most four concurrent requests, and records society Instagram/Facebook links. It excludes the SU's footer accounts and share buttons. It then collects organiser posts from accessible public HTML and Instagram profile embeds, plus an optional authorised Meta API connection. It does not sign into social networks or bypass access controls. A missing account means it was not discoverable in the public profile, not that the society has no account. See [social collection and API setup](README-social.md).

The initial event sources are Durham SU's [What's On](https://durhamsu.native.fm/events) and the public [DAISI Luma calendar](https://api2.luma.com/ics/get?entity=calendar&id=cal-lvIwlKjJGAceOBN), linked from the society's [website](https://durhamaisafety.uk/). Public pages with schema.org Event JSON-LD are also supported. Configure additional sources in `data/sources.json` with `id`, `type` (`ics` or `jsonld`), `url`, `society`, `source_label`, and `timezone` when a source uses local clock times.

The Native adapter follows the public, unauthenticated JSON event-index API used by the SU website, paginates it, and reads each upcoming event's public description from embedded JSON. It never executes page JavaScript. Its `api_url` includes a public page-component identifier, not a secret or access token. If Native changes this identifier or response structure, the source reports errors and retains last good data. Sold-out events are excluded. Native's starting ticket price is retained separately as `price_from`; it does not replace an unknown exact entry `price`. A successful index fetch does not imply every detail page succeeded: `parse_error_count` and the review queue identify partial failures.

Only events with an explicit free-food promise, an exact start date/time, and a source link enter the live feed. Merely mentioning pizza, coffee, a meal, free admission, or an event organiser that sometimes provides food is insufficient. `price` means **entry price in GBP**, not food price. It stays null when unknown; free pizza does not imply free entry. `food_is_free` is true for published entries. Unknown sign-up rules, deadline, end time, eligibility, entry cost, and dietary details remain unknown. Cancelled/postponed structured events are excluded. Recurring/all-day/ambiguous-clock entries go to the review queue; this prototype does not expand recurrence rules.

`data/reviewed-events.json` is the editor input for individually checked social posts and other public sources. It contains `{"events": []}` initially. Every new entry requires `reviewed: true`, `id`, `title`, `society`, `starts_at` (ISO with UTC offset), `location`, `food`, `food_is_free: true`, `source_url`, and `verified_at` (ISO timestamp). Optional keys are `ends_at`, `price`, `signup_required`, `signup_deadline`, `eligibility`, `source_label`, `description`, and `dietary`. Check these against the original post and preserve unknown values as null; do not invent a sign-up link or deadline. `signup_required` is boolean or null. No pasted social text is automatically promoted to a verified event.

Outputs:

- `dist/data/events.json`: `{updated_at, timezone, events, sources, status}`. Event fields include `id`, `source_id`, `title`, `society`, `starts_at`, `ends_at`, `location`, `food`, `food_is_free`, `price`, `signup_required`, `signup_deadline`, `eligibility`, `source_url`, `source_label`, `description`, `dietary`, `verified_at`.
- `dist/data/societies.json`: `{updated_at, source_url, societies: [{name, url, instagram_url?, facebook_url?, socials_checked_at?}]}`.
- `dist/data/social-posts.json`: normalised organiser posts, separate publication/observation timestamps, per-account coverage and provider status. Never includes API credentials or session cookies.
- `data/review-queue.json`: candidates that need human review, with source URLs and reasons. These are never shown as live listings.

`sources` records each fetch attempt, its last success, parsed counts, and errors. `status.state` is `ok`, `partial`, or `error`. `updated_at` is the latest pipeline run, so consult source `last_success_at` and event `verified_at` for freshness. If a fetch fails, last good events from that source remain, with their original verification dates. If the directory fails, its last good snapshot remains. A successful empty source removes withdrawn entries. Invalid manual edits preserve the previous manual feed and report errors. Validated AI events and manually reviewed entries retain their original past dates in the feed. The frontend defaults to future events plus the previous 14 London calendar days, labels previous events as past, and offers the full saved history. It recomputes time status when rendering: feed `temporal_status` is only a snapshot. `total_event_count`, `past_event_count`, `past_14_day_event_count`, `ended_today_event_count`, `started_today_event_count`, and `upcoming_event_count` distinguish history from upcoming opportunities.

Historical AI extractions can be restored without paying for either scraping or model calls: run `python scripts/recover_event_history.py` for a dry run, then repeat with `--write` and run `python scripts/refresh.py --offline` to rebuild the feed. The replay searches collector artifacts under `work/`, or the supplied repeated `--archive-root PATH` locations. It requires exact current post signatures and model-input fingerprints computed from saved PNG bytes, complete image coverage, a successful cached positive decision/extraction, and the same strict event validation used for new results. Missing images, edited posts, incomplete videos and uncertain/nonfree events cannot enter the archive. The raw model cache is unchanged; `data/event-history-report.json` records the recovery. Future AI runs retain past occurrences automatically, and saved Apify posts remain available to validate that history. The 30-day cutoff still controls new paid post collection.

Repeat announcements merge only when the society, UTC start time and venue match (ignoring venue punctuation and case). A manual review wins; otherwise the most recently published source supplies the details. `corroborating_sources` retains the other source links and evidence. A reviewed entry may set `resolves_post_review: true` only after checking the entire source post, to clear its AI review queue; reviewing one date of a multi-event post does not imply that flag. Historical structured-feed events remain when their URL disappears from the source. A currently observed source URL, including an explicit cancellation or changed food offer, supersedes the archived version.

GitHub Actions refreshes each evening at approximately 20:00 Europe/London. Two UTC schedules plus a DST check select the appropriate run; manual dispatch always runs. GitHub can delay cron execution. The workflow's only write permission is repository contents for committing these four data files. Ingestion errors are visible in feed status rather than replacing good data with an empty snapshot. The website shows only verified real listings, with past events clearly labelled. Event suggestions are submitted on the site and stored separately for review; see ../docs/event-suggestions.md.

Useful options: `--directory-only` skips profile crawling, `--skip-societies` uses the saved society directory, `--social-only` collects social posts without refreshing other sources, `--skip-social` retains the social snapshot without social requests, `--workers 2` reduces directory concurrency, `--now 2026-10-17T19:00:00Z` makes date filtering reproducible, and `--root PATH` selects another data/output tree. Run all tests with `python -m unittest discover -s tests -p 'test_*.py' -v`.
